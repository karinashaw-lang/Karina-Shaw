# search/

Data for Phase 5.1's plain-language document search and Phase 5.2's
"which document do I need?" intake flow — both engines live in
`app.js`, next to the clause-matching engine they both reuse the tf-idf
machinery from (`buildClauseIndex()`/`matchPassage()`, the "read a
contract" feature).

## lay_terms.json

Maps each document id to 5-10 plain-language phrasings a non-lawyer
might type into a search box or use to describe their situation — the
synonym/lay-term layer the master plan asks for ("deposit back" maps
to security deposit; "fired" maps to termination). These phrasings are
indexed directly alongside each document's title/description/category
in `buildDocumentIndex()`, so the mapping is structural (a search for
"deposit back" matches the security-deposit document because that
phrase is literally in its index) rather than a separate synonym
substitution step applied at query time.

Generated across all 740 documents by parallel `Agent`-tool workers
(10 batches of 74), each grounded only in that document's own
title/description/categories — no external research needed, pure
paraphrasing. Validated against `lint/advisory_phrases.json` (0 hits
across ~4,170 phrasings — "inform, never advise" applies to search
phrasings too: they describe what someone is looking for, never what
they should do about it) and spot-checked by hand (50 random entries).
183 documents initially fell short of the master plan's 5-phrase floor
(as low as 3); backfilled with additional, non-duplicate phrasings in
a second pass so every document now has 5-7.

## Why this directory has no scripts

Unlike `verifier/` or `watcher/`, there's no orchestration script here
because generating a lay phrasing isn't a research task with an
external, fact-checkable answer — it's paraphrasing from data already
in `data/documents.json`, done directly rather than through a
versioned prompt + harness split. If this data needs regenerating for
new or changed documents later, the same approach (batch documents,
dispatch parallel `Agent`-tool workers grounded in each document's own
title/description/categories, validate against the advisory lint, spot
check a sample) is the one to repeat — see `DECISIONS.md`'s Phase 5.1
entry for the full writeup, including a real precision bug this data
surfaced in the search engine itself (a common filler word getting an
inflated tf-idf weight — see `app.js`'s `STOPWORDS` comment).

## Golden search tests

`tests/search/golden_queries.json` + `tests/search/golden_search.js`
are the master plan's literal 5.1 deliverable ("golden search tests: a
list of 100 lay queries with expected top-3 documents, run in CI").
The fixture was built by `tests/search/generate_golden_queries.js`
(not run by CI) by trying each candidate document's own lay-term
phrasings against the real, live `searchDocuments()` until one
actually placed that document in the top 3 — so every entry in the
committed fixture reflects verified behavior against this engine, not
an aspiration that might not hold. A later failure in `golden_search.js`
means the engine's behavior changed since the fixture was generated,
not that the fixture was ever hopeful.

## intake_flow.json

Phase 5.2's "which document do I need?" intake flow: for each of the
8 declared categories, 2 narrowing questions (the master plan's
"situation category, then 2 to 4 narrowing questions"), each with
2-4 answer options. Each option carries a short `keywords` string
(not shown to the reader) that gets folded into a query alongside the
category name and scored by the same engine as free-text search
(`scoreDocuments()` in `app.js`, restricted to that category's
documents) — so the ranking a reader sees is the real search engine's
output, not a hand-built decision tree mapping specific answer
combinations to specific documents. That would have meant hand-curating
a mapping across up to 16 answer combinations per category (8
categories × up to 16 = well over 100 cases) with no principled way to
check it stayed right as the corpus changed; scoring through the real
engine means the ranking updates itself as documents, lay terms, or
keywords change, the same way free-text search does.

Written by hand (not generated by `Agent`-tool workers, unlike
`lay_terms.json`): there are only 8 categories, and getting the
narrowing questions themselves right — genuinely useful, grounded in
what's actually in that category, and carefully neutral in wording —
is closer to the kind of editorial judgment call this project reserves
for direct authorship than to the bulk paraphrasing `lay_terms.json`
needed.

Every real path through every category's flow (every narrowing-question
combination) is checked in CI by `tests/search/intake_coverage.js`:
each one must actually produce keyword-scored matches within its own
category, not silently rely on `renderIntakeResults()`'s
"nothing matched, show the whole category" fallback — a path that only
ever hit the fallback would mean its narrowing questions do nothing.
88/88 real combinations currently pass on real, keyword-scored
matches.

The results screen heading is always "Documents that match what you
described," never framed as a recommendation — the master plan's own
required wording for exactly this reason: every result still carries
its own real title and description for the reader to judge, the same
as the ordinary picker.

## Related documents (Phase 5.3) — no data file here

Phase 5.3's "related documents" feature (shown on the output screen)
has no data file under this directory: it's computed entirely from
structure already in `data/documents.json`/`data/clauses.json` (shared
clauses, shared fields, category adjacency), not from any precomputed
or generated content. The logic (`relatedDocuments()`, `idfWeight()`,
`buildRelatedDocsIndex()`) lives in `app.js` next to the other two
search engines this directory's data feeds, and its CI test,
`tests/search/related_coverage.js`, lives alongside `golden_search.js`
and `intake_coverage.js` for the same reason. Full writeup in
`ARCHITECTURE.md`'s and `DECISIONS.md`'s Phase 5.3 entries.
